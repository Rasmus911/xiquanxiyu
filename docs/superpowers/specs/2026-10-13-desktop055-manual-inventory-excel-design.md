# 0.5.5 人工盘点与 Excel 库存设计

日期：2026-10-13（北京时间）。状态：聊天方案已确认，书面设计待复核；尚未实现、构建或发布。

## 1. 已确认范围

桌面与网页目标版本 0.5.5，面向 Win10/Win11 的 x86、x64 四个通道，不构建 Win7。
安卓目标版本 1.2.12，版本码至少 19 且必须超过实际已有发布；最低版本码沿用既有配置。
三端连接同一 ECS API 与数据库，服务端决定库存和权限，提交成功后同步刷新。

更新日志原文：

本次不改会员、次卡、收银金额、小票权限、账号注册令牌、手牌芯片绑定或订单打印规则。
经营数据重置继续保留库存。保留历史库存、采购成本、耗材及审计记录。

## 2. 下单与库存分离

桌面、网页、手机下单时取消耗材选择窗口，选中项目后直接提交原订单及打印流程。
本次之后的新订单，无论服务还是商品，都不因下单、撤单、换套票、清空手牌或结账自动改变库存。
不能只隐藏前端窗口：服务端单笔、批量、套票及旧客户端兼容入口均须使用同一人工盘点规则。
旧客户端提交耗材字段不作为库存扣减授权；新订单不生成耗材扣减流水，也不因库存为零阻止项目销售。

迁移前订单已经发生的真实扣减证据保留，旧订单撤销的兼容逻辑继续依据原不可变记录返回库存，
不能伪装成新订单，也不能无原始扣减证据就增加库存。升级前后的行为必须分别测试。
更新窗口先核对未结订单，避免混合版本操作造成无法解释的库存返回。

库存之后仅由采购入库、人工盘点、人工调整及经过确认的 Excel 导入改变。
“人工盘点”与“采购入库”区分：表格数量是最终实存量，不是本次入库增加量。
导入计算差额并记盘点流水，不伪造采购记录或采购支出，也不重新计算原采购预警值。

## 3. Excel 数据与匹配

采用应用导出模板并回导方案。直接 SQL 覆盖库存不能保留版本冲突与追责；
仅按名称匹配也不能可靠处理改名，因此不选这两种方案。

模板只有三个可见业务列：

| 商品名 | 包装成本（元） | 现存基本单位数量 |
| --- | --- | --- |
| 示例奶膏 | 120.00 | 800 |

此示例表示每箱成本 120 元、实际剩余 800 袋；不是 800 箱，也不是剩余库存总成本 120 元。
名称为文字单元格，成本与数量为数值。缺失成本留空，不能把未知成本导出为零。
表格顶部说明成本按每箱、包、桶等入库包装计价，数量按袋、瓶、条等最小单位填写。
应用预览为每行显示真实包装与基本单位，不让工作人员只凭数字判断。

模板附隐藏的项目 ID、导出时记录版本及模板格式版本。它们只用于匹配和提示，不作为权限凭据。
已有行的 ID 保留时允许修改名称；ID 不存在、被改成其他项目或同一 ID 重复须报错，不能静默覆盖。
普通外部表格没有 ID 时，仅允许唯一、精确的名称匹配；去除首尾空白，不做模糊合并。
多个同名项目、重复行、新名称与已有名称冲突均要求人工核对，不能择一覆盖。
新增行的隐藏 ID 留空；更名的已有行不要删除隐藏 ID。
表格遗漏的库存项目不删除、不归档；已归档项目不自动恢复，须在应用里明确处理。

导入先支持 `.xlsx`；旧 `.xls` 文件需另存为 `.xlsx`。
拒绝宏、公式成本/数量、外部链接、损坏压缩包和异常展开大小，避免执行公式或采用旧缓存值。
文件上限 10 MiB、最多 1000 条业务行，解压总大小上限 50 MiB；导入不直接访问文件系统路径。
Excel 名称按普通字符串导出，防止以等号开头的名称成为公式。

## 4. 预览、确认与一致性

流程为“选择文件 → 预览新增及变更 → 确认异常变化/验证必要密码 → 保存 → 查看导入结果”。
预览显示旧值、新值、数量差额、减少百分比、成本单位、新项目及错误行，未变化行默认折叠。
错误行存在时不提交整个文件；修正后重做预览，不采用悄悄跳过错误行的部分成功模式。

原数量 Q > 0 且新数量 N < Q 时，按 `(Q-N)/Q >= 0.25` 触发二次确认，等于 25% 也触发。
服务端用十进制或精确交叉相乘比较，不用浮点近似判断边界。
例：800 袋变成 600 袋触发；变成 600.001 袋不触发。新数量不能为负。
原数量为零时不做除法、不显示减少率；增加和未变化不使用“消耗很多”提示。
提示：“原库存 800 袋，新库存 600 袋，减少 200 袋（25%）。是否是真的消耗了这么多？”
可在同一预览集中确认所有异常行，但每个异常项目必须有明确确认记录，不能只用全局布尔值绕过。

任何导入均需确认预览。空白成本对已有项目表示不修改，数值 0 表示明确设置为零；
空白数量是错误，0 是有效实存量。相同内容不重复写流水。
修改已设置成本须验证当前登录账号的密码；首次设置成本沿用免密码规则。
手机号、姓名和客户端传来的角色不能替代服务端真实权限。

预览绑定文件 SHA256、用户、终端、经营期、当前项目版本及修改摘要，确认提交时重新读取并锁定。
预览后数量、名称、单位、成本或权限有变更则返回冲突并要求重新预览，不覆盖别人的新修改。
整次导入以事务提交，重试使用幂等键返回原结果，不重复扣减或重复创建项目。
记录批次、行号、来源摘要、前后值、确认异常的用户、时间、终端和请求 ID，进入原审计链。
导入不得直接更新账目、绕过库存流水或削弱不可变审计保护。

## 5. 新项目与补齐信息

Excel 新名称及数量、成本先进入持久化“待补资料”队列，不猜测袋、瓶、箱或包装换算。
待补条目在导入结果中可见，顶部红色入口为“补齐库存信息（N）”，仅有库存管理权限的人可操作。
点击后列出缺少资料的项目；在应用填写基本单位、入库包装及每包装基本单位数。
保存前显示“待导入 N 个基本单位、每包装成本 M 元”，完成资料后才创建有效库存与期初流水。
未补齐条目不能用于入库、销售库存关联或成本统计，但不能丢失原表中的数量和成本。
已有项目已具备资料时直接通过预览更新，不强迫重复填写。
旧项目如仍使用“原销售单位”且无法明确换算，也进入待核对名单，不能误当箱成本回导。
用户可取消待补条目，记录取消，不影响已正式入账的项目。

## 6. 包装成本与基本单位成本

编辑界面提供两个联动输入：“每包装成本”和“每基本单位成本”。用户修改一项，另一项自动计算。
按 `包装成本 = 基本单位成本 × 每包装基本单位数`，例如 120 元/箱与 0.6 元/袋、200 袋/箱等价。
以最后明确输入的计价口径与精确数值为依据，不能保存相互矛盾的两份成本。
输入成本保留至少现有两位小数规则；派生基本单位成本以足够精度显示，不能把 120/200 的结果
或其他不可整除成本先四舍五入到分再反向覆盖原包装价格。服务端使用 Decimal，不用浮点金额。
Excel 回导选择包装成本为输入口径；没有包装的物品以基本单位作为其成本单位，换算为 1。

包装成本、计价口径与派生成本需要新增兼容字段，旧成本不清零、不按猜测的箱价迁移。
旧记录若明确基本单位成本和包装换算，显示可推导的包装成本，原历史采购成本记录保持不变。
改变包装规格不改变实际基本单位结存或旧流水换算快照，预览必须同时展示成本换算影响。
成本修改仍保留原账号密码核验和版本冲突检查，包括 Excel 批量修改。
历史报表保持原统计口径；人工盘点差额不是采购成本，不自动算成收入或支出。

## 7. 三端界面与接口边界

库存页保留每页 10 条、右上分页。上方增加“导出库存表”“导入库存表”及红色补齐信息入口。
桌面、网页、手机都使用同一服务端规则，文件导入/导出按各平台文件选择及保存方式接入。
未具备库存写权限的账户不能导入、改成本或补齐项目，原搓澡师/服务员导航权限不扩大。
云端新增受权限控制的导出、预览、确认及待补资料接口；既有库存读写接口保留兼容字段。
新增导入服务与成本换算服务分开，前端只显示预览，不能自行决定匹配、差额、权限或金额。
只有数据库事务提交后发布实时事件，三端同步刷新库存及待补数量；断线恢复拉取权威数据。

## 8. 当前库存表来源

不能以历史照片、历史 CSV 或本机测试数据库冒充当前 ECS 实存量。
首次模板必须来自用户读取的最新云端库存快照，包含项目 ID、名称、数量、基本单位、包装单位、
每包装数量、成本及版本。由用户执行只读 PowerShell/SSH 采集，助手不代为连接 ECS。
结果保存在“发布 部署云端注意事项”下的私有数据文件；不读取密码、不改变云端数据。
收到快照后生成真实模板并核对代表项目的数量与成本换算；若尚未收到，不声称已生成真实库存表。
上线后的导出按钮允许每次重新下载当前库存模板，避免长期依赖过时副本。

## 10. 逐项验收

1. 三端服务、商品、批量和套票直接下单，零库存也不触发耗材选择或新扣减。
2. 新订单撤销无库存变化，旧订单真实扣减按原记录返回，未生成双重流水。
3. 从真实快照导出三列模板，800 袋、120 元/箱、200 袋/箱正确呈现。
4. 800→600 触发 25% 确认；800→600.001、零起始、增加、零成本、空白成本分别正确处理。
5. 修改已有条目、有效更名、新增、重名、归档、缺列、公式、损坏/超大文件均有明确结果。
6. 新条目待补资料数三端一致，单位补齐后一次性入账，重复提交不重复创建。
7. 包装/基本单位输入往返保持口径，无精度丢失；历史采购成本、会员、余额和审计不变。
8. 成本密码错误、越权、预览过期、同期修改、网络重试均不造成部分保存或重复盘点。
9. 增量迁移、真实恢复、API 与清理服务两次心跳、四通道及旧入口公开字节均通过。
10. 至少分别验收 Win10、Win11 的旧版覆盖更新及安卓旧版应用内安装；不能由本机单元测试代替。
11. GitHub 归档有远端恢复证据，最终清理清单明确，不删除最新版依赖与私有发布材料。

本设计只定义已确认需求及安全边界。书面确认后进入实现计划与开发，最终部署代码须来自
本次真实构建、签名和验证结果，不能提前给一个尚不存在的“已完成发布”脚本。
