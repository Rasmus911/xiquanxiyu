# 独立库存、手动耗材与六种桌面安装包升级设计

日期：2026-10-05。状态：用户已确认方案；本地功能实现与测试进行中，尚未部署云端或发布本次安装包。

## 1. 已确认的需求与实施边界

- 收银员和库管具有相同的五项业务模块权限：手牌、会员、小票补打、项目服务、库存管理。不得因此获得管理员、报表、审计、员工管理、退款或数据库重置权限。
- 项目服务中服务和商品均可新增、编辑名称及对客售价；停用项目不出现在日常管理与下单列表。
- 库存不再依赖销售商品目录，可以独立新增、编辑、删除库存项目。
- 下单时人工选择实际消耗的库存及数量，记录每项服务/商品最常使用的库存，为以后关联提供依据；本次不做自动关联。
- 两张照片上的数量已由用户确认为实际剩余库存，而不是历史采购数量。保留原入库单位、包装规格和照片行号，并根据核对过的规格换算成实际消耗单位；采购单价不作为对客售价。
- 用户已明确箱规换算需求：例如 4 箱、每箱 200 袋，应形成 800 袋现存数量。入库可选择箱，实际耗用以袋等最小消耗单位扣减。
- 交付 Win7、Win10、Win11 各 x86/x64 六个桌面安装包和一个新版安卓 APK，统一访问现有 ECS API、数据库和实时事件。
- 不清空会员、余额、历史订单、员工、库存流水或审计链，不删除 ECS 文件；本次升级不包含此前提及的清理任务。
- 本地开发、测试和准备发布资料；云端部署仍由用户执行提供的 PowerShell 指令。不得因为赶时间跳过签名、备份或迁移验证。

五项页面权限首先应用于现有桌面/网页功能。手机同步本次商品、独立库存和手动耗材点单功能，并保留已有角色与受保护管理员身份。手机的会员收银及 USB 小票打印不在本次新建；仍由桌面完成。不得将手机号或显示名称作为管理员授权依据。

## 2. 方案选择

推荐采用“独立库存主档 + 订单耗用记录”。销售目录决定顾客付款金额；库存主档记录实物和单位；耗用记录将订单与实物关联。这样同一耗材可用于多个服务，一个服务也可以选用多个耗材。

备选方案是继续使用商品目录库存，并附加耗材映射。改动表面较少，但清洁用品、包装材料与可售商品仍混在一起，后续维护和单位处理容易混淆，无法完整满足独立库存要求，因此不采用。

本次只实现用户需要的独立库存与人工耗用闭环，不增加采购供应商、会计成本结转、自动 BOM 或手机完整收银系统。

## 3. 权限和日常页面

- 收银员与库管：可开牌、查看/加单、结账及现有会员业务、补打、编辑销售目录、维护库存；服务消费范围为当前允许的全部可售项目。
- 两类员工均不增加退款权、管理员功能或报表权限。受保护管理员现有权限与账号 UUID 保留。
- 服务人员仍按男浴、女浴、三楼岗位限制手牌和服务范围；不能修改目录价格、库存或员工权限。
- 权限同时在服务端、页面菜单、路由和按钮检查；不只隐藏菜单。修改其他员工不会撤销当前操作者登录。
- 手机按已有渠道准入规则开放对应点单与库存/目录能力，不借本次升级绕过渠道保护。
- 默认销售目录仅展示启用项目；管理员可通过独立“已停用”筛选查看历史项目、重新启用，不硬删除已被账单引用的项目。
- 售价调整继续沿用现有规则：未结账成功订单按现有规则实时更新，已结算订单的名称与金额快照不被追溯修改。

## 4. 库存主档与照片初始化

库存主档至少包括：稳定 ID、名称、类别、基本消耗单位、入库包装单位、每包装基本单位数量、原始包装规格、以基本单位计的现存数量、预警值、启用/归档状态、并发版本号。数量与换算使用定点小数，不使用浮点数。

- 一个主档只使用一种基本消耗单位，例如袋、瓶、条、个；包装单位例如箱、件、包。支持明确设置换算关系，不凭品名猜测单位。
- 示例：包装单位“箱”、基本单位“袋”、每箱 200 袋，入库 4 箱自动增加 800 袋；耗用 1 袋后余额 799 袋，可辅助显示为 3 箱 199 袋。基础余额始终以袋记账，不能一处用箱一处用袋直接相减。
- 增加项目时填写名称、基本单位、入库包装单位、箱规及期初数量；期初数量可以按箱或基本单位输入，预览换算后产生可追溯入库流水。
- 入库和盘点记录输入的单位、数量、换算系数快照与基本单位数量；后续修改每箱规格不追溯改变已有余额、历史入库和订单耗用。已发生流水后不直接改变基本单位；变更基本单位必须通过另建项目和明确调整处理。
- 散装货可直接按基本单位入库；“1*200”还须核对 200 对应袋、瓶或其他单位。无法辨认最小单位的照片行留在核对表，不猜填后入账。
- 删除在 UI 表现为删除/归档：零余量直接归档；有余量时明确显示将报损的数量并要求二次确认，写报损流水再归档。历史流水和订单耗用不会删除。
- 对有历史数据的现有商品库存迁移为独立主档，保留对应旧 ID 映射和数量，不重写历史流水。
- 原图出现重叠的第 22—24 行只处理一次。不要仅凭品名相似就合并不同包装/规格的行。
- 照片转录输出核对表，含原图序号、行号、品名、规格、单位、剩余数量、可辨识程度。看不清的字段明确标为需核对，不能编造品牌、单位、数量。
- 初始化采用人工预览确认的盘点导入，逐行展示照片原数量、原单位、规格、基本单位和折算余额；确认后将已映射项目的余额调整到折算后的实际数量，而非在现有余额上再次累加。无法安全匹配的项目新建；未被照片覆盖的现有库存不自动清空。
- 导入保存来源摘要、操作者、变更前后数量和幂等标识；同一导入重复执行不得重复入库。期初/盘点导入本身不产生营收。

## 5. 手动耗用、撤销与使用频次

下单选择服务或商品后，在同一界面展开“消耗库存”。工作人员选择一个或多个库存项目、填写每项总耗用数量，或明确选择“本项不消耗库存”。不允许系统默默沿用上次的耗材选择。

- 库存选择显示基本消耗单位、以基本单位计的当前数量、包装规格，支持搜索；扣减数量是这条订单行的总量，不再次乘订单数量或箱规。下单默认按基本消耗单位选取数量，箱规仅供工作人员参考。
- 一个订单行允许多个库存项目；库存选项不能受销售目录分类限制，但仍需库存启用且操作者具有该下单范围权限。
- 下单与扣库存在服务端同一事务完成。库存不足、无权限、版本冲突或无效输入时全部回滚；前端不能以修改价格或库存请求字段规避检查。
- 服务端使用现有财务写入串行化、幂等、业务期间和并发保护机制；重复点击、网络重试只能生成一份订单和一份耗用。
- 新版本显式选择耗材后，不再叠加旧商品自动扣库存逻辑，避免双扣。
- 兼容旧客户端请求时，保留旧商品自动扣减的现有行为；响应明确返回兼容行为，不能把未提供耗材字段的旧请求误当作“不消耗”。上线设最低兼容版本前先验证手机及桌面更新流程。
- 撤销订单只返还该订单实际记录的耗材及数量，一次且仅一次；不重新根据目前的项目名称、售价或推测映射返还。已归档耗材仍允许按历史耗用返还，并提示管理员存在归档余额。
- 结账本身不再次扣库存；金额与耗材数量独立。
- 使用频次按有效订单行计数：同一订单行某库存出现一次算一次使用；同时记录耗用总量。撤销行不计入有效次数。不同单位之间不比较数量。
- 统计按服务/商品的稳定 ID 聚合，展示“使用次数最多的库存”和次数；并列时展示并列项。重命名、改价不切断关联。统计来源保留到明细耗用记录，未来升级才允许自动关联。

## 6. 数据与跨端同步

增加独立库存主档、订单耗用明细及来源/统计查询；保留旧库存流水的引用关系，通过新增兼容字段关联独立主档。需覆盖已有业务期间重置、数据库角色授权、审计与迁移机制，不单独开一条绕过保护的写入路径。

订单成功写入后统一提交，再发送手牌、库存与目录/布局的对应实时事件。三端重新拉取服务端权威数据；离线期间不声称已经同步，重连后重新加载。事件采用现有业务版本、期间与会话检查，旧响应不得覆盖新状态。

增加/编辑/归档库存、目录改名改价、耗用、返还和盘点导入记录操作者、操作时间、终端、关联订单、前后值、请求 ID。审计链、历史订单与金融流水继续受现有防修改机制保护。

## 7. 六种桌面包、安卓包与发布

复用当前 `client/electron/target-profiles.cjs` 与通用 Windows 构建/签名/发布工具，生成六个明确标注系统及程序架构的包。现有 operations 发布工具只接受 Win11 x64，必须扩展或建立本次独立发布清单，不能直接混用旧部署脚本。

- Win7 x86、x64 使用现有 Electron 22.3.27 兼容配置，仅承诺 Win7 SP1 的目标支持；该运行时已停止安全维护，不能宣称与现代 Windows 具有同等安全性。保留隔离、权限校验、签名更新及服务端保护，但这些不能消除旧系统与旧运行时的漏洞风险。
- Win10/Win11 复用既有现代运行时配置。Win11 没有 32 位操作系统；`win11-x86` 指在 Win11 64 位系统上运行的 32 位应用，不标成“Win11 32 位系统版”。
- 六个包使用同一业务版本、同一 API、独立对应目标的更新通道，更新不能串架构或串旧运行时。验证安装目标、更新签名、发布序号、防回滚与下载摘要。
- Android 延续原签名证书和包名，按更高版本号/版本码覆盖安装，保留现有更新入口。签名密码由用户在本地隐藏提示中输入，不写入聊天、脚本常量、构建日志或压缩包。
- 将六个桌面 EXE、正式 APK、云端 SOURCE/WEB 包、SHA256 清单、版本说明和完整 PowerShell 构建/部署指令集中放到一个新的版本输出文件夹。不同包名称明确，文件夹不能混入冒充最新版的旧产物。
- 制包成功、自动测试通过与实际系统验收是不同状态。没有实机/虚拟机证据的 Win7/Win10/Win11 架构组合标记为“尚未实机验收”，不得声称已适配验证。

兼容性依据：

- Electron 官方：[旧版 Windows 停止支持公告](https://www.electronjs.org/blog/windows-7-to-8-1-deprecation-notice)。
- Microsoft 官方：[32 位和 64 位 Windows 常见问题](https://support.microsoft.com/en-us/windows/experience/compatibility/32-bit-and-64-bit-windows-frequently-asked-questions)。

## 8. 验收与交付条件

1. 服务端权限测试证明收银员和库管五模块可用、敏感管理员模块不可用；其他员工范围不扩大，三个受保护手机管理员仍能登录。
2. 库存独立增改删、箱规换算、非零余额归档、盘点幂等、旧数据迁移及审计均有自动化验证；验证 4 箱 × 200 袋 = 800 袋、耗用 1 袋后 799 袋、撤销后 800 袋，修改箱规不改变历史余额；照片核对表不重复、不把采购价当售价。
3. 桌面/网页/安卓的下单可选择多个耗材及数量，库存不足整单失败；两终端并发不能超卖、重复提交不双扣。
4. 撤销按原记录返还一次；结账不再扣库存；有效使用频次及并列项正确。
5. 三端实际验证库存、改价和手牌实时刷新、重连刷新、退出登录后的权限隔离。
6. 六种安装产物身份、文件摘要、签名更新与安卓版原证书验证通过；按能够提供的系统环境分别标记实机验收状态。
7. 云端在备份、恢复验证与迁移演练通过后由用户切换；更新策略只发布验证过的产物，不覆盖原有无关发布配置，不删备份。

## 9. 实施顺序

先完成权限和服务端独立库存/耗用闭环，再同步桌面网页及手机 UI，随后校对照片初始化资料，最后制包、生成发布清单和 PowerShell 指令。每个阶段进行对应回归测试；失败时停在当前阶段，不输出假成功的最新版安装包。

用户已确认本方案，具体任务见同日实施计划。构建、签名、云端部署与实机验收结果分别记录，不将本地测试等同于线上发布成功。
