# 溪泉洗浴：员工权限、点单体验与正式价目表升级设计

日期：2026-10-04（北京时间）

状态：用户已于 2026-10-04 书面确认。套餐不重复计费、男浴 001–050 / 女浴 051–100 及本文全部升级边界已经确认。本文不是已完成开发或云端部署的声明。

执行中补充（2026-10-04）：用户要求本次**只交付Win11 64位桌面包**，其它现有目标及旧包不删除、不覆盖。必须核查于在跃、李丽娜、于景辉三位既有绑定管理员的手机登录/通道关闭问题；按实际UUID绑定修复和提供诊断，不凭姓名放行或关闭校验。该补充替代之前六包构建要求。

## 1. 目标与实施路径

基于现有 Vue、Flask、Electron、Android 系统增量升级，不更换技术栈，不新建另一套数据库。桌面、网页、手机仍访问同一个 ECS API 和 PostgreSQL。

可选路径及取舍：

1. **推荐：分模块增量升级，一次受控发布。** 先修复账号授权和会话错误，再完善点单，再引入新目录与套票计费，最后统一构建、迁移、验收。能保留既有打印、会员、支付和升级机制，但需要覆盖跨模块回归测试。
2. 分多次发布，每次只处理一个模块。每次变更较小，但客户需要多次更新、服务器需要多次维护，价目表与前端可能存在过渡期。
3. 重写管理端和移动端。可以重新组织全部交互，但工作量、数据迁移和回归范围更大，不作为本次方案。

本次按第一条组织四个模块：账号和权限、点单界面、业务目录和计费、发布与版本控制。各模块有独立测试，使用一份一致的数据契约。

## 2. 已确认的业务边界

- 收银员新增“小票补打”权力，最终营业主页面为前台手牌、会员管理、小票补打。结账、充值、买次卡属于这些主页面的业务子流程，不因减少导航而禁用。
- 库管只显示库存管理营业主页面。
- 男浴搓澡师、女浴搓澡师、三层服务员只显示手牌点单营业主页面。只看已经激活、尚未结清的手牌，不得开牌、结账、管理会员、修改价格或库存。
- 既有最高管理员全部保留。继续使用既有账号 UUID 绑定身份，不凭姓名相同或前端传入 admin 判定最高权限。店主重置能力仍只属于当前绑定店主。
- 男浴现用编号改为字符串 `001` 至 `050`，女浴改为 `051` 至 `100`，各 50 个，手工输入号码保持全局唯一。
- 套票包含门票及相应项目，按套票价格收费；同一手牌的套餐内项目不得重复收费。
- 本次不清空会员余额、历史结算、库存流水或审计日志，也不重新执行之前的业务重置任务。

## 3. 员工创建、授权、启用、删除

### 3.1 已定位的源码问题

当前员工创建在生产权限策略下强制停用；启用时又只接受固定最高管理员名单。针对目标员工的普通操作拒绝返回 `CHANNEL_FORBIDDEN`，桌面请求拦截器因此清除正在操作的管理员会话。

这解释了“启用新员工时自己退出登录”的代码路径。实现阶段仍需用隔离测试重现，不将源码推断当作已经验证的修复。

### 3.2 普通员工授权

- 管理员在同一个员工表单中录入账号、姓名、角色、密码、允许使用的入口和启用状态。保存成功后列表立刻反映实际授权结果；不出现前端显示已启用而服务端实际停用的情况。
- 普通角色采用服务端固定权限模板，不允许客户端提交任意权限字符串。入口授权按员工 UUID 保存，不能依赖终端编号前缀或姓名。
- 角色与入口必须匹配。默认：收银员桌面/网页，库管桌面/网页/现有手机库存页，搓澡师及三层服务员桌面/网页/手机点单。手机本次不新建会员管理、收款结账、小票补打模块，因此收银员不开放手机业务入口。
- 新建普通员工不自动进入最高管理员名单；既有最高管理员策略不被普通员工增删改覆盖。
- 已有非最高管理员账号保留原资料，不批量启用或擅自授权；管理员可逐个编辑授权并启用。
- 修改员工角色、密码、入口或启用状态，只提升该员工的会话版本并撤销其旧会话。不为一次普通员工操作提高全局策略版本，不让其他管理员集体掉线。
- 单次业务操作越权返回动作级权限错误，不清除有效操作者会话。账号真实停用、会话撤销、入口撤销、经营期变更或全局策略失效，仍必须停止操作并退出登录。

### 3.3 删除是可追责的逻辑删除

- 员工列表增加删除按钮及确认提示。删除后停用、撤销授权、踢出该员工全部终端，并从正常员工列表隐藏。
- 数据库保留该员工 UUID、用户名、历史订单、库存操作和审计关联。用户名不回收给新账号，避免历史责任混淆。
- 管理员可以通过“已删除账号”筛选查看保留记录，但不能通过普通启用开关直接复活已删除账号。
- 禁止删除自己、绑定店主及既有最高管理员；此类身份不由普通删除功能处理。
- 审计记录包括操作者、目标账号 UUID/用户名、时间、终端、请求标识、原角色/状态及变更结果。密码、令牌和签名口令不进入日志。

## 4. 页面与 API 的权限矩阵

| 身份 | 桌面/网页营业主页面 | 手机营业主页面 | 关键限制 |
| --- | --- | --- | --- |
| 既有最高管理员 | 全部既有管理页面 | 全部既有手机业务页 | 店主重置仍按绑定 UUID 单独限制 |
| 收银员 | 前台手牌、会员管理、小票补打 | 不开放 | 可以正常开牌、加单、收款、充值和补打；不能改目录价格、看报表或管理员工 |
| 库管 | 库存管理 | 库存管理 | 可以查询库存与出入库；不能修改服务价目表、收款或进入手牌页面 |
| 男浴搓澡师 | 手牌点单 | 手牌点单 | 仅男浴已激活手牌；仅搓澡类服务和对应可售商品 |
| 女浴搓澡师 | 手牌点单 | 手牌点单 | 仅女浴已激活手牌；仅搓澡类服务和对应可售商品 |
| 三层服务员 | 手牌点单 | 手牌点单 | 男女浴已激活手牌；仅休息/按摩类服务和相应商品 |

登录、退出、必要连接设置、个人会话信息属于辅助流程，不算额外营业主页面；不借辅助页开放管理功能。

现有 manager 角色保留既有管理职责，不自动升级为最高管理员；不增加用户未要求的新管理角色。

实施要求：

- 菜单、首页落点、路由和按钮由同一服务端能力定义产生；手输网址也不能绕过路由检查。
- API 独立检查动作权限、入口、目标手牌浴区和商品服务范围。不能只隐藏菜单或只过滤列表。
- 库管查库存所需商品资料属于内部数据读取，不因此获得“项目商品”或“系统设置”页面。
- 将“加单”权限与“开牌/换牌/联动/清空/收款”权限区分。搓澡师与服务员可点单，但不能因为点单需要而获得前台管理动作。
- 联动组的序列化也按浴区过滤。男浴员工不能从男浴手牌的 linked_visits 字段取得女浴详情；女浴同理。
- 手机的最高管理能力不再由是否有 `mobile:order` 推断，防止普通点单员工意外获得全部浴区、全部商品、报表或库存管理。
- 实时通知只发给有权限的订阅者；收到事件后仍通过授权 API 读取当前数据。断线或后台唤醒必须重新拉取，不声称离线时仍实时同步。

## 5. 联动手牌、顶部加单与排序

### 5.1 快速切换和隔离草稿

当前联动标签只变更 `/visits/:id` 路由，但组件复用时没有监听 id 重新加载；加上页面整体遮罩，容易表现为点不动或内容不更新。

- 点击联动标签立即显示选中状态，监听路由 id 加载对应账单。只给需要更新的内容显示加载状态，手牌切换栏不被整页遮罩挡住。
- 为请求加递增序号或取消旧请求；快速点击 A、B、C 时，只有 C 的最新响应能够更新当前页面。
- 草稿按 visit UUID 隔离。切到另一张手牌不会把上一张选中的商品带过去，返回后可恢复该手牌未提交草稿。
- 点击“加入手牌”时先固定目标 visit UUID、商品 ID、数量和幂等键。提交途中不允许把同一提交转给另一张手牌；对选错、已经结清或版本冲突给出明确提示。
- 返回前台保留男女浴筛选和滚动位置；保留已有联动单独结账、多选结账及全部结账行为。
- 草稿在登出、经营期重置、目标结清或权限撤销时失效。不可在后来重开的同号手牌上复用旧 visit 草稿。

### 5.2 提交按钮

- 桌面快速加单卡片标题栏右上角放“加入当前手牌”主按钮，旁边显示选中种类、商品件数和金额；当前手牌号清晰可见。
- 手机在选择区域上方同样提供提交入口；窄屏不足时标题和操作换行，不能挤出屏幕。可保留适合触屏的底部摘要，但不能出现两个互不一致的提交状态。
- 商品可加减多个；服务每次点击默认一次。无选择、提交中、失去连接或目标手牌失效时禁用提交。
- 搜索、分类、选中效果和清空选择继续保留。Enter 只在明确搜索/提交上下文生效，Esc 可关闭弹层；输入框内不触发无关全局快捷键。

### 5.3 管理员拖拽布局

- 在快速加单选择区提供管理员“调整排列”模式；普通营业模式点击仅选项目，不意外启动拖拽。
- 快速加单增加默认“全部”视图，允许服务和商品混排，同一排可以出现“搓澡、搓泥宝”。保留服务、商品及分类筛选；类型标签和商品数量控件仍区分实际业务类型，不能为混排而把商品伪装成服务。
- 修改以“保存排列”一次提交，不每移动一格就写数据库。关闭编辑时未保存修改可丢弃；不影响消费草稿。
- 手机支持拖拽手柄和触屏操作；同时提供上移/下移作为键盘和无拖拽设备的备用方法。布局适配 Win7 对应旧 Chromium。
- 顺序保存在 ECS，由最高管理员修改；采用快速加单目录的一份全局顺序，员工和三端经权限或类型过滤后显示相应子序列。
- 使用目录排序版本和完整快速加单目录 ID 集合原子保存。拒绝重复 ID、不属于快速加单目录的 ID、缺失 ID 和旧版本覆盖；失败时提示刷新，不部分写入。门票票种和挂失赔偿不混入普通加单排序。
- 搜索、类型或分类筛选状态下不允许提交残缺的排序集合；进入排列模式先切换“全部”并显示完整可排列目录。
- 保存后发送授权的目录变更通知，并记录调整前后顺序及操作者。服务端 ID 是顺序的唯一依据，不能凭客户端名称匹配。

### 6.5 旧目录处理

- 活跃服务、旧门票和旧套票替换成以上正式清单；“删除旧服务”指不再可售，不物理删除被历史订单引用的条目。
- 既有饮品、食品、其他商品及其库存保留。澡巾若唯一匹配既有一次性搓澡巾，可原 ID 改成新名称/价格并保留库存和旧订单名称快照；匹配不唯一时停止迁移，输出待核对 ID，不自动合并。
- 新建备品、搓泥宝等库存商品初始数量为 0，通过正式入库录入实际数量。不能凭空生成 10 件或清空既有库存。库存不足正常阻止售出。
- 挂失赔偿 20 元保留，不作为普通服务删除。
- 更改启动种子逻辑，旧服务、旧编号不会在重启后自动补回；升级后不得每次启动重写员工修改过的价格、库存或排序。
- 迁移提供预览及带确认的应用步骤，具有唯一迁移标识并可重复执行，不产生重复项目、不重置已迁移库存。

## 7. 套票计费与责任记录

### 7.1 账单规则

- 套票按单个 visit UUID 生效，不因手牌联动自动让其他人获得该套餐。每张手牌最多一份有效套票；不同联动手牌可选择不同套票并分别结账。
- 套票选择/更换/撤销属于前台计费动作，只允许收银员和相应管理员。搓澡师、三层服务员不能设置收费套餐或改票价。
- 套票本身形成一条按总价收费的订单记录。包含的门票以及可匹配正式目录的服务/商品，每项最多覆盖一次。
- 购买前已点的同名包含项目优先覆盖最早的一份；购买后再点时，尚未使用的包含额度先覆盖一次。超过一份的额外服务/商品按正常单价收费。
- 被覆盖的已实际点单项目保留原价/数量/操作者证据，标明“套票内”，应收金额为 0；不删除已履行项目，不用撤销冒充免费。
- 套票只是购买计费权益，不自动把所有项目标为已做，也不自动发放全部耗材。套餐商品实际加入手牌时扣库存；已有商品若已扣库存，仅改变收费归属，不再次扣库存。
- 商品一次选多件时，包含额度只覆盖一件，其余按单价计算。库存扣实际总件数。
- 未结账前更换或撤销套餐，服务端重新计算现有实际点单项目的收费归属；失去包含额度的项目恢复正常应收。没有实际点单的套餐说明项目不生成额外费用。
- 已结算账单金额、支付和原小票不得被目录调价或套餐变更改写。保持现有授权退款流程，不把本次套餐撤销扩展成已结账改单。

示例：成人门票 15 + 搓澡 10 + 男/女浴拔罐 15 已开单，选择套票 A 后，这三条显示套票内，套餐应收 45；另买矿泉水 3，应收总计 48。重复另加一次拔罐，不再覆盖，增加 15。

### 7.2 技术和资金约束

- 包含关系按服务端保存的目录 ID/套餐定义判断，不按客户端名称、价格或零金额判定。
- 服务端行锁、版本检查和幂等键保护套餐、商品扣库存和结账。重复点击/网络重试不得增加第二份套餐或重复扣库存。
- 小票、结算预览、联动合计、单独结账、报表分类和审计证据使用同一应收口径。套餐收入只入账一次，零应收包含项目不能再次记为收入。
- 套餐定义/价格更改继续遵守未结账实时重算规则；只影响相应未结账记录，已结账快照不变。重算不能把“套票内”金额意外恢复为全价。
- 库存调整与收费优惠是两种独立动作；覆盖、换套餐不能重复生成出库。实际撤销商品时才按原销售记录一次归还库存。
- 保存套餐定义快照、覆盖明细、价格变化前后金额、操作账号/终端/时间/请求标识，供对账和追责。普通账号不能改审计链、订单原金额或签名验证逻辑。
